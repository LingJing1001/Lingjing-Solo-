# 统一 R3 设计：兼容全部比赛的搜索型规划层

> 日期：2026-09-18
> 目标：把现在散在 8 个文件里的"R3"收成**一个内核**，既不让 LS20 / AR25 / R11L 的既有成绩回退，又能吃到没写过专用代码的新游戏。
> 依据：本文每条约束都带 file:line 证据；未验证的推断会标「假设」。

---

## 0. 一句话结论

R3 必须是**双层搜索**（配置层 → 动作层）跑在**一个内核**上，游戏差异全部下沉到一个声明式 profile（状态键 / 资源通道 / 动作候选生成器 / 进度信号），并且内核只能建立在**画面 + step()** 这一套线上可得的信息上——今天最能打的几个"R3"（快照回滚搜索）在线上根本不可用，它们的正确身份是**离线解法工厂**。

## 1. 三条硬约束（决定架构，先摆出来）

**C1 线上拿不到引擎对象。**
`arc_agi/remote_wrapper.py`（`RemoteEnvironmentWrapper`，第 17 行起）里没有任何 `_game` 属性，只有 `reset()`(79) / `step()`(139) 走 HTTP POST；`_game` 只存在于 `local_wrapper.py:69`。
⇒ 凡是靠 `env._game` + `set_level()` + `snapshot/restore` + `perform_action(raw=True)` 的实现都不能上线：
`C:\newtask-pi\tools\ls20_solve_v4.py`、`arc_adaptor/arc_shadow.py:41`、`run_ar25_r234.py` 的 `r3_state_search:361` / `r3_beam_search:411`、`ft09_solver.py:169` 的 reset+重放 BFS。

**C2 线上每一步都不可撤销，且错了要掉计数器。**
唯一可回的分支信号是 `FrameData`（`arcengine/enums.py:131-140`）：`state / levels_completed / win_levels / full_reset / available_actions`。
⇒ 线上"搜索"= 在**学到的/自建的**转移图上预演，落地一步、核对预测、错了就重规划。这正是团队自己那份 `docs/搜索算法和胜利检测.pdf` 写的路线：用 WorldModelField 的 `(s,a)->s'` 建图，步代价 1，成环代价 ∞，BFS/Greedy-Best-First 找路径。
⇒ 例外：`available_actions` 含 ACTION7(UNDO) 的游戏可以真回滚，那是线上版的 snapshot/restore（见 B4）。

**C3 不要在最差的空间里搜。**
`docs/ar25-pruning-spec-from-arcsage.md` 的 0 节已经用血泪写过："不要在 ACTION1–5 的动作树上硬 DFS/Best-First 冲 L7"，Lingjing 旧报告的贪心 Best-First（300s / 60 万节点超时）就是"在错误搜索空间里烧预算"；ARC-SAGE 可复现的路径是**先枚举终态配置**（块坐标 × 镜轴坐标）→ 反射闭包判覆盖 → 再反推短路径。
⇒ 这就是"双层"的由来，也是它必须写进内核、而不是只写在 AR25 里的理由。

预算事实：提交模板 `agents/templates/lingjing_solo_agent.py:46` 是 `MAX_ACTIONS = 800`；`PLAYBACK_FPS = 5` 只是节奏不是硬限（`agents/agent.py:265-268` 只做 sleep）。远端 HTTP timeout 10s。⇒ 单步规划按 1–2s 限流，全局按"剩余动作数 + 剩余墙钟"双闸门。

## 3. 设计

### 3.1 分层决策顺序（保证不回退）

```
T0 罐头路线      CannedRoutePlugin / script_bank        已验证解优先，命中即用（LS20 309 / AR25 276）
T1 专用在线规划   LS20View 等 profile 的 path 求解        保住 L1-L2 这类已能在线过的关
T2 通用 R3 内核   配置层搜索 + 动作层搜索（本文主体）      新游戏的主路
T3 探索兜底       advisor / explorer 信息增益             零分风险的对冲
```
上一层只在"有把握"时短路；任何一层通关就 `full_reset`/换关并重新选层。**T2 追平 T1 之前不许退役 T1。**

### 3.2 内核协议：`WorldView`（每游戏一份声明，唯一允许的游戏知识）

```python
class WorldView(Protocol):
    # —— 观察 → 抽象状态（禁止把资源计数器放进键，支配剪枝才成立）
    def grids(self, frame) -> list[np.ndarray]: ...        # frame.frame 是 list：见过 (1,64,64)/(2,64,64)/(6,64,64)/(17,64,64)
    def key(self, grids) -> Hashable: ...
    def counters(self, grids) -> dict[str, int]: ...       # 单调不增通道：剩余步/生命…，可为空
    def proposals(self, grids, key) -> list[ActionSpec]: ...# ★ 动作候选生成器（见 3.3）
    def config_space(self, grids) -> ConfigSpace | None: ...# ★ 配置层（见 3.4）；None 表示只有动作层
    def score(self, grids) -> float: ...                    # 启发式/目标分，可退化
    def progress(self, frame) -> int: ...                   # 默认 = frame.levels_completed（通用，零分支）
    def done(self, frame) -> bool: ...                      # 默认 = frame.state is WIN
    def dead(self, frame) -> bool: ...                      # GAME_OVER 或某个 counter 掉了
```
`progress/done` 的默认实现直接吃 `FrameData` 的官方字段——这是"兼容所有比赛"的地基：**进度和胜利不需要认识游戏**。PDF 里"输出网格 == 目标网格"式的判据保留为可选第三信号（用于 `levels_completed` 不动的游戏）。

### 3.3 动作候选生成器（统一 LS20/AR25/R11L 三种交互范式）

分支因子是统一 R3 的真敌人：LS20 是 4 个方向，AR25 是 4 方向 + SELECT + 镜轴位置，R11L/VC33 是 `ACTION6(x,y)`，定义域 64×64 = **4096**。
⇒ 内核**永不**枚举 `available_actions × 参数域`。profile 必须交 `proposals()`，其语义是"从画面提出的、值得试的少数动作"：
- LS20：4 邻居格（`DIRS` + `_walkable`，已有）
- AR25：`enum_useful_positions`（`run_ar25_r234.py:89`）——把块推到目标/反射位
- 点击类：连通域质心、UI 元素中心、上一轮有效点击的邻域（`exploration/click_sweep.py` 已是这个思路的采样版）
候选质量决定一切，所以 `proposals()` 要带**在线自我扩展**：某动作有效但候选里没有它 → 记进该 profile 的候选表（对应 `transfer/` 的技能库），下一层搜索就有。

### 3.4 配置层优先（把 arcsage 的教训固化）

有 `config_space()` 时先搜配置：`目标终态 = (各块位姿, 各轴坐标, …)`，判据是覆盖/匹配谓词（AR25 是反射闭包 `covered ⊇ targets`；LS20 是三元组 `(shape,color,rot)` 相等）。配置解出来后交给动作层做 **pathify + 校验**：
- pathify：在学到的图/模拟器上做 BFS 求实际步序列（AR25 的 `_generate_actions` 是手写的推广版）
- 校验：arcspacesage 规格点名的坑——纯几何枚举会给出因碰撞不可达的配置（AR25 L7 理想 `(8,1)`，实际赢在 `(8,11)`）。所以配置解**必须**经过"真执行一次"的验证才算数。
没有 `config_space()` 的游戏直接进动作层，此时 noop + 计数器支配两条剪枝是唯一的空间压缩手段，必须默认开启。

### 3.5 剪枝契约（内核写死一次，四条）

| 名字 | 判据 | 现有同物 |
|---|---|---|
| P1 noop | `key(child) == key(parent)` → 丢 | v4 `if k == akey(s)`；`field.py:188 noop_streak`；`advisor.py:66 "noop_effect"` |
| P2 计数器支配 | `best[key]` 存该键见过的最大 counter；`child.counter <= best[key]` → 丢；出堆再核一遍 | v4 `best_counter`；`simulator.py:243` 键不含 `steps_used`；`field.py` 键不含步数 |
| P3 死亡 | `state==GAME_OVER` 或 lives 通道下降 → 丢 | v4 `if g.aqygnziho != s[6]` |
| P4 预算 | `g + h > budget`；budget 来自 counters 或剩余动作数 | `solver.py:170`；`r234` 的 `>= ilqnjlrnkk-1` |

P2 的前提是"键里不含计数器"，这条要写成内核断言（profile 若把计数器塞进 key 就直接报错），否则支配剪枝会静默失效——这是最容易犯、最难查的错。

**断言的实证依据（2026-09-19 在 AR25 引擎上量得，见 `arc_adaptor/arc_shadow.py:157-192`）。** `_state_key` 是 `_snapshot` 的**有意掩码投影**，不是原样拷贝：

- 掩掉 `lelsvjlwneo.current_steps`。AR25 存在真实的状态等价：L7 那块 7×3 的 `0006lxjtqggkmi`，`np.rot90(px,2)` 的**数组与字节都等于原数组**，且 `tvqhikkvjs`（`environment_files/ar25/0c556536/ar25.py:1295-1306`）的重定心让转 180° 后 `(x,y)` 也回到原值 ⇒ "转半圈"是伪装成动作的 noop，只消耗一步。计数器若进键，这种状态每步都"新"，noop/支配两条剪枝同时失效、搜索原地打转。**"键不含计数器"不是洁癖，是 P1/P2 的成立条件。**
- 掩掉 `ovoizfolxfq`（每块到轴的距离表）。它是纯缓存：`vrkougbfel`（同文件 1287-1293）= `abs(精灵中心 − 轴坐标)`，两侧都已在键里，掩掉零信息损失。⇒ arcsage 规格那句"state_key 必须含旋转距离表"**不需要显式字段**：旋转落在 `pixels`+`x,y`，距离落在两者之差。
- 掩掉 `hujpxmlafgh`（赢了等跳关）与 `_state`：终态走 `solve_level` 的显式判定（313/317 行），不混进等价类。
- 掩掉 `xukxeewuexo` / `xjwpeqpcxav`：step() 开头对非 ACTION5 每次重置（1699-1701），属动作派生量而非状态。
- 留在键里的 `hsiusrsrdkswnt`（L2 教程动画闩）看着像该掩的相位，实测无碍：`perform_action` 内部 `while not is_action_complete(): step()`（`arcengine/base_game.py:222-234`），动画 8 帧期间 `step()` 自己 early-return，搜索取到的恒为静止值 {0, −1}，等价于一个 one-shot 位。内核仍应要求 profile 只登记**静止态**标量。

`arc_shadow` 的一处差距要记着，别当范本抄：它的键已经不含计数器，但**没有**做成 P2，只有一个 push 前写入的 `seen`（320-322 行）配 `h*10+len(path)` 的强启发优先级——先占坑的路径不保证省步，与它"不追求最短"的目标自洽，但谁要拿最短解必须换成 `best_cost[key]` + 出堆判定（内核按 P2 实现即可同时满足两者）。

### 3.6 资源通道自动发现（新游戏没有 HUD 知识时的出路）

`counters()` 不该要求人先去读每个游戏的 HUD。通用做法：**挖掘单调通道**——观察所有画面派生标量（某行色块连续段长度、某色像素计数、某区域精灵数），保留"跨步单调不增、且偶尔下降"的那些，作为 P2/P4 的通道。
已验证实例：LS20 步数条 = 第 61 行 x∈[13,56) 的色 11 连续段，右端给出剩余与上限（`ls20_solver.read_step_bar`，今晚实测驱动了 L2 的补给绕行并第一次在线过 L2）。自动发现器要能把它当"发现出来的通道"重新推出，才算通用。

### 3.7 后端（`expand()` 的四种实现，内核不关心）

- **B1 EngineBackend**（离线专用）：真引擎快照/回滚 = 今天的 v4 / arc_shadow。用途：生成与更新 T0 罐头解、当回归基准。产物仍写进 `script_bank`。
- **B2 SimulatorBackend**：纯 Python 自建模拟器（`ar25_solver/simulator.py` 已存在）。最省线上步数，但按游戏写，属 profile。
- **B3 LearnedGraphBackend**：线上默认，`field.predict_graph`。带不确定度：majority_ratio 低的边加惩罚，走错就重规划并把纠错边回写。
- **B4 UndoBackend**：`available_actions` 含 ACTION7 时，真执行 + UNDO 即线上合法的回滚 ⇒ 把 B1 的搜索搬到线上。假设：仅部分游戏有，需按 C2 的 `available_actions` 探测，不可写死。

  **B4 前置判据（2026-09-19 修正，原写法过强）：undo 恢复的状态维度必须 ≥ 本游戏 `key()` 的维度，否则 B4 会给出"以为回滚了"的假解。** AR25 就是反例：`siizypdewv`/`neimtgmbvs`（`environment_files/ar25/0c556536/ar25.py:1309-1327`）的 undo 快照 `flqblmrxsla` **只存块与轴的坐标**——不恢复 `pixels` 旋转、不恢复选中对象 `yvifanjrcyu`、**也不退还 `current_steps`**。而它的 `_state_key` 含 pixels 与 `_sel_idx` ⇒ 在 AR25 上按 ACTION7 当回滚，搜索会拿着被污染的计数器/旋转态继续推。
  ⇒ B4 的启用条件要写成一次探测：进某游戏前，先在本地/影子上做一次 `act → undo → 比对 key()` 是否回到原值；只有回到才允许线上用 B4。探测失败 ⇒ 退 B3，且把"该游戏 undo 不等价"记进 profile。
  同源提醒：`arc_shadow._snapshot` 自己也没覆盖 `flqblmrxsla` 与 `_current_level_index`（靠 285 行阉割 `next_level` 兜住，`neutered` 失败即失守），所以 B1 也不是无条件可信的。

线上一层只允许 B3/B4；B1/B2 属离线工厂。这条边界要在代码里用 `is_local` 断言，防止"离线能跑、上线静默退化"。

## 5. 风险与取舍（摊开）

- **线上探索要花真步数。** 走错一次就掉计数器，所以内核的目标函数不是"最短解"而是"置信度加权的最短解"；预测不确定的边要收信息税（`advisor.py` 的 hypothesis 扩展可复用）。这是与离线搜索最本质的区别，别照搬 v4。
- **像素状态混叠。** LS20 换关当帧仍渲染上一关，是我在 L2 白花 8 步才定位的坑。通用处置进内核：动作后画面未变 → P1 noop；画面变了但语义键回到旧值 → 判混叠，延迟一步再确认。
- **候选生成器是单点风险。** `proposals()` 提不出正确动作，配置层再准也没用。要保留"有效动作回灌候选表"的通路，并给 T3 探索留预算。
