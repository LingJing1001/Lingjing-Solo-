## 1. 问题：为什么"晶格"必须先通用化

闭卷路线的定位数字（`docs/M1整改_Step1/2A/2B/2C`）：

```
strict 闭卷（CB=2）  0.6200  ← 纯通用件（CEAX + heatmap 点击）
                    3.1312  ← + 两个手写求解器（tu93 7 关 + ar25 1 关）
```

也就是 **80% 的闭卷能力来自两个手写求解器，通用件只占 20%**。而这两个求解器的**第一步完全相同**：

```python
# closed_book/tu93_frame.py（改前，33 行）
def detect_lattice(arr):
    for orow in (0, 1, 2):          # ← cell = 3 写死
        for ocol in (0, 1, 2):
            score, active, cells = _purity_and_cells(arr, orow, ocol)
            ...
# closed_book/ar25_frame.py（改前）
CELL, GRID_N = 3, 21                # ← 尺寸、格子数、origin 全写死
n = min(GRID_N, h // CELL, w // CELL)
```

两个求解器加起来只注入了 6 类结构先验（晶格 / 动作语义 / 调色板角色 / 关系规则 / 目标 / 搜索），
其中 5 类项目已有骨架。**本轮做第 1 类：晶格。** 它排在第一位是因为：后面 5 类全都以
"格子坐标"为输入 —— 拿不到格子，后面都无从谈起。

## 2. 方案：一份只看像素的晶格检测器

新增 `lingjing_solo/core/lattice.py`（纯 numpy，无引擎/无表/无存档读取）：

```python
from lingjing_solo.core.lattice import detect_cell_lattice

spec = detect_cell_lattice(frame)           # frame 或 ndarray 都行
spec.cell      # (3, 3)
spec.origin    # (2, 1)   ← 逐关变化的相位，逐帧重算
spec.cells     # (21, 21) 每格多数色
spec.sweep     # 诊断：每个尺寸的纯度扫描曲线
```

### 2.1 度量：实心度（solidity），不是"精确纯色"

一个候选 `(尺寸, 相位)` 把画面切成格子，每格打分：**它是不是"一块颜色"**。关键是给
**格内装饰**留容差 —— 装饰恰恰是真实游戏的常见画法：

| 真实例子 | 格内像素 | 精确纯色 | 实心度（容差 1/8） |
|---|---|---|---|
| tu93 危险砖（8 号色 + 1px 朝向点） | 8 + 1 | ✗ | ✓ |
| ar25 光标框（形状格里 1px 描边） | 8 + 1 | ✗ | ✓ |
| **错误相位**（骑在格子边界上） | ~5 : 4 | ✗ | ✗ |

容差取 `(格子面积 - 1) // 8`（≈12%，尺度一致：3px 格放 1px，8px 格放 7px）。
所以 tu93 的纯度 0.9841、ar25 的 0.8611 都被拉回 **1.000**，而错相位仍然停在 0.0–0.35。
纯色帧除外：整格背景色的格子**不计入**（画面大部分是空的会让任何尺寸白拿满分）。

### 2.2 选尺寸：实心度落差（solidity cliff），不是纯色度

纯度永远选不出尺寸 —— `cell = 1` 对任何画面都是 100% 实心。所以：

> 在**够实心**（≥0.75）且**证据够多**（≥4 个信息格）的尺寸里，取**实心度落差最陡**的那个：
> `argmax_s [ purity(s) − purity(s+1) ]`，并列取更小尺寸。

这就是"**画面在哪个尺度上还是块常数、再粗一档就崩**"。真帧上的落差非常干净：

```
tu93 真帧：  s=1:1.000  2:0.335  3:1.000 ← 落差 0.95   4:0.055  5:0.179  6:0.234  7:0.242  8:0.280
ar25 真帧：  s=1:1.000  2:0.427  3:1.000 ← 落差 0.95   4:0.056  5:0.182  6:0.242  7:0.381  8:0.353
原生像素帧： s=1:1.000 ← 落差 0.65       2:0.350  3:0.330 ... （没有任何粗尺寸够实心 → cell = 1）
```

`cell = 1` 不算候选（它是"这就是一张像素网格"的诚实答案），所以**没格点的游戏不会被硬塞一个格子**：
cd82/ls20/r11l/tn36 这类直接返回 native，调用方按普通像素网格处理。

### 2.3 成本：积分图 + 相位网格归约

朴素实现是"每个相位 reshape 一次" → `O(s² · H · W)`，64×64 全扫描要 44 ms/帧，逐帧调用不可接受。
观察：**每个格子起点在所有相位里恰好只属于一个相位**，所以

- 每个颜色建一张积分图（前缀和）→ 任意 `size×size` 块的多数色计数是 4 次查表；
- 把块计数图 padding 到 `size` 的整数倍 → 一次 `reshape(a, s, b, s).sum((0,2))` 就把**全部 s² 个相位**同时算完。

→ 每尺寸 `O(颜色数 · H · W)`，与相位数无关。全扫描 8.1 ms/帧（改前 44 ms），
钉住尺寸（`sizes=(1,2,3)`）4.7 ms/帧。**等价性有测试兜着**：快扫 vs 逐相位参考实现在 7 张帧 × 9 个尺寸 ×
两种容差模式下逐字段相等（`tests/test_lattice.py::test_fast_scan_equals_the_reshape_reference`）。

### 2.4 确定性：tie-break 与 legacy 逐字节一致

并列时取**更小尺寸、更小相位**，与 legacy tu93 扫描的 `(purity, active)` 排序一致；
并且 `tolerance=0` + `sizes=(3,)` 时，通用检测器**就是**那份 legacy 扫描（同一条测试断言了这点）。
这是"通用化不改变已计分行为"的形式化依据。

## 3. 接线：通用优先，legacy 兜底

| 位置 | 改法 |
|---|---|
| `closed_book/tu93_frame.py` | `detect_lattice` → 先跑通用检测器（`background=VOID`，全尺寸扫描）；只认 3px 结果，否则回退 `_legacy_detect_lattice` |
| `closed_book/ar25_frame.py` | `_to_cells` → 几何由通用检测器给（`background=COL_BG`）；读出非 3px 或退化时回退硬编码 21×3/origin(0,0) |
| `perception/__init__.py` | 再导出 `detect_cell_lattice / LatticeSpec / lattice_sweep / to_cell_grid` |

**为什么放 `core/` 而不是 `perception/`**：closed_book 的模块契约要求"不拖入重型依赖"。
实测 `import lingjing_solo.<任何子模块>` 都会经 `lingjing_solo/__init__.py → .agent` 拉起全线
（perception/planning/…，366 ms / 17 个子包），所以 `core/lattice.py` **不增加任何成本**；
反过来放 `perception/lattice.py` 只会让"这份纯几何"多背一层包初始化。`core/lattice.py` 只 import numpy，无环依赖。

## 6. 已知边界（别把它们当成 bug）

1. **稀疏帧上的"大尺寸偶发实心"**：画面只有两三簇图案时，粗尺寸可能碰巧全实心。
   用 `floor=0.75` + `min_support=4` 挡（真帧上 tu93 的 s=6 落在 0.234，安全）；
   即使偶发命中，代价也只是"求解器读不懂 → 落到 CEAX"，不会产生错误动作。
2. **对齐诊断只认周期的倍数**：`lattice_sweep` 里的 `align` 在 2×cell 处同样高（每两条线仍是一条线），
   所以它**只做诊断、不参与决策**，选尺寸交给实心度落差。
3. **只扫方形格**：`LatticeSpec` 带 `cell_r/cell_c`（`_measure` 支持矩形），但检测只枚举方形 —— 目前
   25 个游戏里没出现矩形格点，先不做。
4. **每帧成本 8 ms**：闭卷求解器逐帧调用，tu93 整局约 200+ 次解析 ≈ 1.6 s，可忽略；
   若某游戏解析频率极高，用 `sizes=(...)` 钉住尺寸（4.7 ms）或缓存 spec（同关卡内相位不变）。
