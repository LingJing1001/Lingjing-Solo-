## 1. 问题：为什么角色推断是第 3 类里"唯一真要写的"

两个手写求解器的**第二步完全相同**：给自己认识的颜色起名字。

```python
# closed_book/tu93_frame.py
VOID, CONNECTOR, CORRIDOR = 5, 2, 0
PLAYER, HEADING, TARGET = 9, 4, 14
DOORS, GEMS, HUD, DEADLY = (12, 13), (11, 15), 6, (8,)

# closed_book/ar25_frame.py
COL_CURSOR, COL_REFLECT, COL_SHAPE = 0, 4, 5
COL_BG, COL_AXIS, COL_TARGET = 9, 10, 11
```

Step 4 解决了"格子在哪"，本轮解决"**格子里这块颜色是谁**"。
它是唯一必须真写的一类，因为其余四类都能复用现有骨架（见 §9），
而**角色是所有下游先验的输入**：不知道谁是玩家，就无从谈"动作语义"（谁在动）、
"关系规则"（谁跟谁镜像）、"目标"（要覆盖谁）。

## 2. 方案：`lingjing_solo/core/roles.py`

```python
from lingjing_solo.core.roles import infer_roles, RoleTracker

spec = infer_roles(frames, actions, levels, states)   # 整条轨迹 -> 一份角色快照
spec.background  # 5
spec.avatar      # 9   <- 玩家：格空间里唯一"刚性平移 + 与动作方向一致"的颜色
spec.hud         # {6} <- chrome：原地重绘、从不平移、体积小
spec.mirror      # 4   <- 反射：单轴镜像
spec.cursor      # 0   <- 贴着头像的稀疏细标
spec.attached    # {4} <- 骑在头像体内的实心装饰（tu93 的朝向点）
spec.terrain     # 墙 / 走廊 / 轴 / 靶 —— 用排除法得到
spec.goal        # 只在观测到**升级**时投票
spec.lethal      # 只在观测到**死亡**时投票
spec.note        # 证据不足时**明说自己不知道**（"no mobile block seen"）
```

### 2.1 两个空间：**运动量在格空间，装饰量在像素空间**

这是整个模块最关键的一个决定，且它是被真实帧逼出来的：

tu93 的玩家是 3×3 的格，**每一步会在不同位置挖掉一个 1px 的"朝向点"**，
所以"颜色 9 的像素集合"**不是**上一步的刚性平移：

```
实测 tu93 某一步：真值格空间位移 = (-2, 0)
                 像素 bbox 位移 = (-5, +1)   ← 假的
```

在**像素空间**做刚性匹配会咬住那个假位移，动作一致率只有 **48%**；
在**多数色格网格**上装饰被量化掉，格子整体平移整数格，一致率 **95%**（lag 2，138 次真实移动）。

所以：

| 问题 | 度量空间 | 产出 |
|---|---|---|
| **什么在动** | **格空间**（每格多数色） | `mobile` / `avatar` / `mirror` |
| **画了什么** | **像素空间** | 晶格外 chrome、1px 光标、骑在头像里的装饰 |

### 2.2 渲染滞后：帧落后于动作，且**逐游戏不同**

tu93 实测 **lag 2**（lag 2 一致率 95%，lag 0 = 36%，lag 1 = 33%），且**玩家一步走 2 格**。
所以匹配时**不假定动作和帧对齐**，而是在 `range(MAX_LAG+1) = 0..3` 里取**得分最高**的 lag。
ar25 的合成场景是 lag 0，真帧也落在窗口内 —— 同一段代码两头都对。

### 2.3 绝不猜：证据门控

`goal` 只在**观测到关卡递增**时投票（"消失的/被踩到的颜色"）；
`lethal` 只在**观测到死亡**（`state ∈ {LOSE, GAME_OVER}`）时投票（"尝试进入的那个颜色"）。
没有证据就留空并在 `note` 里写明 —— 宁可说"不知道"，也不给下游一个错的敌人。

另外两条纪律：

- **关卡运行不得混池**：同一颜色号在不同关卡含义不同（ar25 会重画轴），
  `levels` 变化时清空全部累加器；且 **RESET 导致的关卡数下降不算升级**。
- **移动的玩家不是 chrome**："每步都变"同样描述了被指挥的方块，
  所以动画规则只对**从不平移**的颜色生效（格空间**或**像素空间任一在动都排除）。

### 2.4 HUD 的三重判据

1. **在晶格外**：像素有 ≥60% 落在格子区域之外（且"外"本身要够大，
   `HUD_OUTSIDE_MIN_FRAC = 0.05` —— 64×64 帧里 21×21 板子只留 1px 边=3.1%，
   那条边是**板内容被画布裁掉**，不是面板）；
2. **原地自绘**：重绘率 ≥ 0.9、体积小、每帧在场、**并集 bbox 面积小**
   （这一条把 tu93 的门/宝石挡在外面：它们同样重绘 97%、体积也小，但每个待在不同格里，
   并集会横跨约 1000 px）；
3. **会动的颜色不算 chrome**。

### 2.5 同色多职：取最大连通块

ar25 的**颜色 5 既是可动形状、又画着面板**，所以"颜色 5 的 bbox"是**整个画面**，
于是每个小颜色都像"骑在头像上"。取**最大连通块**（`_largest_component`）才是那块形状。

### 2.6 `cursor`（细）与 `attached`（实）

两者都随头像变化，只能靠**形状**分开：

- `cursor` —— 稀疏细标（ar25 实测 5px / 7×7 框，fill **0.10**）；
- `attached` —— 骑在头像**体内**的实心小色块（tu93 朝向点是 1×1，fill **1.0**）。

判据是 `fill ≤ 0.75`（`OUTLINE_FILL` 卡在真帧的 0.10 与实心 1.0 之间）。

## 3. 接线：旁证 + **默认关闭**的兜底

| 位置 | 改法 |
|---|---|
| `closed_book/tu93_frame.py` | 新增 `roles_probe(frames, …)`（旁证）与 `parse_frame_with_roles(frame, roles)`（用推断的**玩家**色解析）；`parse_frame` 抽取为 `_parse(…, player_colour=PLAYER)`，**签名与行为不变** |
| `closed_book/ar25_frame.py` | 同上；`parse_frame_with_roles` 覆盖 **shape / cursor / reflect** 三色（axis 本来就靠几何恢复，target 保持常量） |
| `closed_book/tu93_solver.py` | `LINGJING_ROLES_FALLBACK=1` 时，`parse_frame` 失败才用推断色重试；**关闭时不构造 tracker** |
| `closed_book/ar25_solver.py` | 同上；补 `_last_act`（推断需要"动作↔位移"锚点，见 §6.3） |

**为什么只覆盖玩家，不覆盖目标/门/宝石**：玩家是唯一有**正信号**（刚性平移 **且** 与动作方向一致）
的角色；目标/陷阱猜错会把规划器**指向致命格**。兜底是用来**解卡**的，不是用来**猜**的。

**为什么默认关**：闭卷口径要能逐位复现。开关关闭时连 `RoleTracker` 都不实例化，
`solver._roles` 保持 `None`（有测试断言这点），所以出货路径的行为与改前**逐字节相同**。

## 6. 本轮修掉的三个真问题（都不是"顺手改测试"）

### 6.1 一个真 bug：`not cursor` 对颜色 **0** 求值为 `True`

平局仲裁里写着：

```python
if avatar is not None and not cursor and not attached and len(ranked) > 1:
```

ar25 的光标色**恰好是 0**，而 `not 0 == True` —— 于是一次**正确**的读数
（`cursor=0`）被当成"没有光标"，仲裁被错误触发，把 avatar 从 5 交给了亚军 0，
真主角反被降级成 `attached=[5]`。真帧没暴露它，只因 ar25 真帧的亚军是色 4
（`agree_rate` 0.64 ≠ 1.0 → 循环 `break`）。

修复：`cursor is None`。**合成场景比真帧先抓到了它** —— 这就是保留合成测试的理由。

### 6.2 一笔测试债：格空间重写后没回头跑合成测试

`roles.py` 从"像素空间"重写成"格空间"时，`tests/test_roles.py` 没同步更新，
留下 **8 条红灯**（期望 `_prev` 单帧、朝向点在 `mobile`、ar25 光标画成实心框……）。
本轮把它还清：测试**没有放宽**，而是**改成忠实于真帧**：

- `ar25_like` 的轴**画成 1 格宽（3px）** —— 1px 的线会打断 3px 周期，
  检测器随即退化到 `cell=1`，于是所有度量掉回像素网格（这正是模块要避免的）；
- `ar25_like` 的光标改成 **7×7 内 5px 的稀疏星**（fill 0.10），与真帧一致；
- `tu93_like` 的 HUD **默认逐帧变长** —— 真帧的计时条是会重绘的，
  而"静态 HUD 不被认作 chrome"恰恰是模块的规则。

### 6.3 ar25 的推断拿不到动作锚点

`RoleTracker` 靠"动作 ↔ 位移一致"认头像；而 `ar25_solver` 原先**不记录上一步动作**，
兜底只能传 `action=None` → 推断不出 avatar。已补 `_last_act`（用单点赋值包装
`next_action`，规划主体原样不动）。

## 7. 已知边界（别把它们当成 bug）

1. **`goal` / `lethal` 常为空**：它们被证据门控，短轨迹里没有升级/死亡就不投票。
   这是设计，不是缺陷 —— 下游要的是"已知的敌人"，不是"可能的敌人"。
2. **晶格外判据在 21×21/64px 布局下必然沉默**：外面只有 1px 边（3.1%）。
   tu93 的 HUD 是靠**自绘**抓到的，真帧与合成场景一致；该判据留给**粗晶格**游戏（如 su15 的 5px）。
3. **镜像是"单轴反射"，不是"完全取反"**：ar25 只翻列，竖直移动两者同向。
   要求"翻转那一轴"实操 ≥2 次才算数，否则一个只是"跟着走"的颜色会靠两个零分量蒙分。
4. **兜底只覆盖玩家（tu93）/ 形状+光标+反射（ar25）**：目标与陷阱保持常量，理由见 §3。
5. **`RoleSpec` 是普通类，不是 `@dataclass`**：bench 用 `spec_from_file_location` 加载 agent
   且不注册 `sys.modules`，模块级 dataclass 会在解析注解时 `AttributeError`
   （与 `lattice.LatticeSpec` 同一个坑）。
6. **成本**：每步一次布尔归约/颜色 + 小色的一次裁剪刚性匹配，**不保留任何帧**
   （除"当前帧/上一帧"及其格网格孪生），可全程在线调用。
