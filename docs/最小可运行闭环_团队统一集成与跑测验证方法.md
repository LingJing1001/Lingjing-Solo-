# 最小可运行闭环：R2 / R3 / R4 / R5 / CEAX 与 R11L 团队统一集成与跑测验证方法

> 文档状态：团队协作设计基线
> 生成日期：2026-09-18
> 适用项目：`Lingjing-Solo-`
> 目标：把不同成员、不同游戏、不同跑测方法统一到同一条**可重放、可审计、可分层验收**的最小闭环中。

---

## 1. 结论先行

最小可运行闭环不是另起一个“大一统 solver”，而是固定一条所有模块都能接入的证据链：

```text
环境 FrameData / 游戏状态
        │
        ▼
[R2] 观察与因果记录
        │  Observation + state/action transition
        ▼
[R3] 候选计划 / 路径 / 目标分解
        │  Plan + action candidates
        ▼
[R4] 探索剪枝 / 预算 / 反馈归因
        │  Decision + rationale + evidence refs
        ▼
[R5] 反思 / 假设冲突处理 / 技能迁移
        │  Reflection context + one legal action suggestion
        ▼
执行一个合法动作
        │
        ▼
环境返回 settled frame / state / level / score
        │
        └──────────────回到 R2，形成下一 tick

每一局结束：
recording → replay → Field/Learner 重建 → verification report
                           │
                           ├─ Simulator evidence
                           ├─ Offline engine evidence
                           └─ Live/Scorecard evidence
```

**CEAX 不是替代这条闭环，而是上层环境控制与迁移底盘：**

- 已知/可适配游戏：CEAX 的 Inline/Plugin 路径调用统一 Agent/AR25 adapter；
- 未知游戏：CEAX 负责探索、动作模式、可见性和环境适配，但仍输出同一格式的 observation、decision、transition 和 verification evidence；
- AR25 是闭环中最小的“学习候选 → 引擎重放 → 覆盖/通关验证”执行单元，不是 CEAX 的全部能力。

---

## 2. 为什么需要统一闭环

当前团队存在三类不兼容：

1. **模块边界不同**：R2 偏观察和状态建模，R3 偏搜索/寻路，R4 偏探索剪枝和反馈，R5 偏反思/技能迁移，CEAX 偏未知环境控制；如果各自直接调用游戏 API，产物无法互相消费。
2. **游戏语义不同**：AR25 是轴、拼块、目标覆盖和离线引擎 replay；LS20 是动态障碍、形状/颜色/旋转和在线 Scorecard；CEAX v3.6 还覆盖 click、keyboard、hybrid 和 camera-following 游戏。
3. **“通过”定义不同**：模拟器返回了动作、离线 solver 找到配置、recording 能解析、官方 Scorecard 生成，这些都不是同一等级的成功证据。

因此统一目标不是强迫所有游戏用同一个 solver，而是统一：

- **输入协议**：每个 tick 都能表达 frame、合法动作和环境状态；
- **输出协议**：每个决策都能表达 action、理由、候选和证据引用；
- **状态协议**：每次动作都形成 `(state_before, action, state_after)`；
- **回放协议**：recording 能在没有真实环境写操作时重建 Field；
- **验收协议**：明确 simulator、offline、live 三种证据各自能证明什么。

## 3. 五个模块的角色、当前实现与兼容边界

### 3.1 R2：观察、状态编码、世界模型事实层

**职责**：把连续 FrameData 和动作反馈转换成后续模块可以查询的结构化因果信息。

当前代码和设计依据：

- `lingjing_solo/perception/encoder.py`：帧差分、连通域、轻量特征；
- `lingjing_solo/world_model/field.py:23-177`：状态哈希、transition table、版本、访问状态、Phi/泡壁、WIN 记录；
- `/mnt/c/JWang/2026/Projects/Lingjing/learning/R2-evaluation-and-plan.md`（Windows C: 文档，通过 SSH alias `192-wsl` 读取）定义 R2 的角色为 Layer 0/1 感知、世界模型、转移、规则/目标假设和胜利检测接口；
- `arc_adaptor/r2r3r4_combo.py:28-93` 提供了旧式、面向 AR25 的 R2 结构提取示例。

R2 必须输出至少：

```json
{
  "observation_id": "run/tick",
  "game_id": "...",
  "episode_id": "...",
  "tick": 12,
  "frame_ref": "frames/000012.json",
  "grid_shape": [21, 21],
  "state_hash": "...",
  "state": "NOT_FINISHED",
  "levels_completed": 0,
  "legal_actions": ["ACTION1", "ACTION2"],
  "objects_or_features": {},
  "visibility": "full|partial|unknown"
}
```

**不能把视觉变化本身当作成功。** `delta_pixels > 0` 只能说明环境变化；通关必须由权威 `state=WIN`、`levels_completed`、score 或游戏专用目标验证确认。

**兼容要求**：R2 允许每个游戏有 profile/encoder，但必须最终映射到统一 observation 和 transition。未知字段放入 `game_specific`，不得改变公共字段语义。

### 3.2 R3：目标分解、路径和状态空间搜索

**职责**：消费 R2 的 observation、状态哈希、合法动作和世界模型，生成可执行候选计划；不负责伪造 WIN，也不负责最终证据判定。

现有实现/入口：

- `arc_adaptor/r2r3r4_combo.py:194-260`：通用 BFS/A*；
- `arc_adaptor/agents/strategies/run_ar25_r234.py`：AR25 的目标分解、beam search、`arc_shadow` 状态空间搜索回退；
- `examples/run_ar25_r3_goaldecomp.py`：AR25 单轴目标分解与搜索回退；
- `examples/run_ls20_r2r3r4.py:78-161`：LS20 的 A*、路径缓存和 R4 评分回退；
- `docs/ARC-AGI3-adapter-architecture.md:89-148`：策略通过 registry 按 `game_id` 选择，adapter 不应塞入游戏专用路线分支。

R3 的统一输出应为：

```json
{
  "plan_id": "...",
  "planner": "ar25_goal_decomp|astar|beam|state_search|generic",
  "input_state_hash": "...",
  "candidate_actions": ["ACTION5", "ACTION2"],
  "expected_goal": "cover_all_targets|reach_target|unknown",
  "cost": 15,
  "search_budget": {"time_ms": 30000, "max_nodes": 128000},
  "validity": "candidate|verified_offline|expired",
  "evidence_refs": []
}
```

**兼容要求**：R3 可以有游戏专用 planner，但 planner 只能返回 abstract action name；动作到引擎枚举的转换由 ARC boundary adapter/CEAX environment adapter 负责。不能把 Windows 路径、私有绝对路径或某个成员本地 checkout 写入公共跑测入口。

### 3.3 R4：探索剪枝、预算、热点探测和反馈归因

**职责**：在 R2/R3 候选上做成本约束和证据驱动的决策：信息增益、目标奖励、反循环、探测预算、fail-closed。

当前状态依据：`docs/R4-status.md`：

- `lingjing_solo/exploration/explorer.py` 已记录 `information_gain`、`loop_penalty`、`goal_bonus`、总分、输入顺序和选择原因；
- `step_probe()` 已修正为严格预算语义；
- `infer_goal()` 能消费权威 WIN/level 反馈并写入 `GoalHypothesis`；
- `action_diff.analyze_recording()` 能处理 RESET、嵌套 action payload 和多层 frame stack；
- 真实 LS20 recording 已完成 action diff → `WorldModelField` replay；
- 已明确未验证项：AR25/ft09 原始 recording、真实 harness action payload、重启接管、部署回滚。

R4 的统一决策输出应为：

```json
{
  "decision_id": "...",
  "input_state_hash": "...",
  "selected_action": "ACTION5",
  "candidates": [
    {"action": "ACTION5", "score": 0.72, "reason": "information_gain"}
  ],
  "rationale": "...",
  "probe": {"mode": "none|dry_run|execute", "executed": false},
  "reflection_ref": "reflection/...",
  "evidence_refs": ["observation/...", "plan/..."],
  "fail_closed": false
}
```

**硬规则**：

- 非法 action、未知 action、坐标越界、action/mode 不一致：拒绝，不降级成“看起来能跑”；
- dry-run 必须明确 `executed=false`，不能作为真实环境成功证据；
- keyboard 游戏不允许误用 click probe；
- 探测失败时返回空 action plan 或安全 fallback，不调用未授权 harness；
- 视觉 delta 不得直接提升成功置信度。

### 3.4 R5：反思触发、战略顾问与技能迁移

**职责**：消费 R2 的 `FieldSnapshot`、最近转移、规则/目标假设、循环和预算信号，在 R3/R4 不能稳定推进时进行受控重估；同时把跨关卡/跨游戏可复用的机制经验沉淀为技能先验。R5 是决策建议器，不是执行器，也不能修改环境、规则或历史记录。

当前实现分为两条互补路径：

1. **Layer 4 Reflection Trigger**：`lingjing_solo/reflection/reflector.py:13-87` 监控循环陷阱、规则冲突、步数预算告急三类信号，并在触发后打包 Φ 场摘要、最近转移和合法动作。
2. **Transfer/Skill architecture**：`lingjing_solo/transfer/layer.py:16-235` 维护 `SkillLibrary`、`CompetingHypotheses`、`CounterfactualWorldModel`、`CounterfactualPlanner` 和 `RuleTransfer`；在 observation 时记录实验和假设，在 level/episode 边界抽取技能，在决策时融合技能先验、反事实 ranking 与 R4 exploration score。

R5 固定的安全边界来自 `lingjing_solo/reflection/skill.py:1-24` 和 `reflection/prompt.py:50-79`：

- 只能从当前合法动作列表中建议一个动作；
- 环境摘要、规则和目标只当作数据，不当作指令执行；
- 不请求网络、不读取密钥、不执行文件操作、不改变评测规则；
- 没有合法动作时返回 `None`，交由上层安全降级；
- R5 建议必须记录触发原因、上下文摘要、输出动作和是否被 R4/strategy 接受。

R5 的统一输出应为：

```json
{
  "reflection_id": "...",
  "trigger": ["loop_trapped", "rule_conflict", "budget_warning"],
  "input_state_hash": "...",
  "context_ref": "artifacts/field-snapshot.json",
  "hypotheses": [{"name": "blocked_transition", "confidence": 0.62}],
  "skill_refs": ["movement_family:v1"],
  "suggested_action": "ACTION3",
  "action_is_legal": true,
  "accepted_by": "r4|strategy|fallback|none",
  "evidence_refs": []
}
```

**R5 与 R4 的边界**：R4 负责预算、候选评分、probe gate 和 fail-closed；R5 只提供基于上下文的战略建议。R5 不能绕过 R4 的合法动作检查、模式隔离或预算限制。R5 与 R3 的边界是：R3 生成路径/候选计划，R5 在循环、规则冲突或信息不足时建议最有区分度的下一动作，不直接替换搜索器。

**R5 与 CEAX 的边界**：`TransferLayer` 可以给 CEAX/Agent 提供技能先验，但技能命中率或迁移建议不能直接当作真实通关证据；必须继续经过环境执行、R2 transition 和最终 verification。

### 3.5 CEAX：未知环境控制与跨游戏迁移底盘

**职责**：在更高层管理未知游戏、动作模式、可见性、环境控制和迁移；不取代 R2/R3/R4/R5 的公共证据协议。CEAX 可以消费 R5 的 skill/context，但不能把 R5 预测当作终态证明。

依据：`docs/CEAX_v36_团队技术参考_2026-09.md`、`docs/CEAX_未知破零优先级.md`：

- v3.6 focus8 已达到 7/8 非零，`su15` 已达到 L1，`bp35` 仍为 0；
- click/pull 只对纯 click-family 开放，hybrid/keyboard 必须门控；
- hybrid mutate 目前仍是待攻方向；
- CEAX 入口为 `scripts/bench_ceax_priority.py --max-steps 400`，Agent build tag 为 `ceax-primary-unknown-v3.6`。

CEAX 与本闭环的接法：

```text
CEAX environment controller
  ├─ 选择 observation mode / action family
  ├─ 管理 camera、可见性、settled frame
  ├─ 调用 R2 encoder 生成统一 observation
  ├─ 调用 R3/R4 生成 candidate/decision
  ├─ 在触发时调用 R5 生成 reflection/context/action suggestion
  └─ 写入同一 run manifest + JSONL recording
```

**Inline/AR25 关系**：AR25 是 CEAX 在已知机制游戏上的可验证 Inline 执行单元；CEAX 的未知游戏探索不能因为某个 AR25 离线 solver 通过，就宣称未知游戏能力已经通过。

## 4. 与 `projects/ARC-AGI-3-Agents` 的集成回顾与变更要求

### 4.1 当前集成方式

两个项目不是通过复制整个 Lingjing 工程耦合，而是通过 `Lingjing-Solo-/arc_adaptor/` 向 ARC checkout 提供一组**边界适配包**：

```text
ARC-AGI-3-Agents official runner
  ├─ FrameData / GameAction / GameState
  ├─ agents.Agent lifecycle
  └─ agents.__init__.py registration
          │
          ▼
ARC agents/templates/lingjing_solo_agent.py
          │
          ├─ FrameData → numpy grid
          ├─ legal actions normalization
          ├─ LingjingSoloAgent.observe()
          ├─ GameStrategyRegistry.resolve(game_id)
          ├─ strategy output → GameAction (+ x/y for complex action)
          └─ illegal/empty output → safe fallback or RESET
          │
          ▼
Lingjing-Solo core + R2/R3/R4/R5/CEAX evidence pipeline
```

当前实现证据：

- `arc_adaptor/agents/templates/lingjing_solo_agent.py:43-120` 是官方 ARC `Agent` 的薄边界适配器；
- `arc_adaptor/agents/strategies/registry.py:12-28` 按 `game_id` 路由 `LS20Strategy`、`AR25Strategy`、`R11LStrategy` 和 `GenericStrategy`；
- ARC checkout 通过 `agents/__init__.py:11,21-55` 暴露 `LingjingSolo`；
- `sync_to_arc.sh:23-30` 只复制 adapter、strategies、tests 和 tools；
- `sync_to_arc.sh:32-38` 的 recording patch 是可选的，不能默认认为已应用；
- `tests/unit/test_lingjing_solo_agent.py` 覆盖 frame 转换、registry、AR25、LS20、R11L 和 empty-action fail-closed；
- `tests/unit/test_r11l_probe.py` 覆盖单通道 frame、frame hash、click diff 和 terminal/level evidence。

### 4.2 同步边界和不能改变的事项

`Lingjing-Solo` 是 source of truth，`ARC-AGI-3-Agents` 是官方 runner/runtime checkout。同步必须使用：

```bash
cd /srv/agent-platform/projects/ARC-AGI-3-Agents
bash ../Lingjing-Solo-/arc_adaptor/sync_to_arc.sh .
# 只有确实需要 ARC 原生 recording 改动时才使用：
# bash ../Lingjing-Solo-/arc_adaptor/sync_to_arc.sh . --with-recording-patch
```

已修复的集成 blocker：`lingjing_solo/exploration/__init__.py` 原有 `ft09_solver` 导入括号未闭合，且仓库没有对应模块；已移除失效导出并通过 ARC adapter targeted collection 回归。随后补齐了 `LS20Solver` 的公共导出、`reset/set_plan/next_action` adapter 兼容边界；这些变更不等于线上 LS20 通关证据。

必须注意：

1. **不要手工把 `Lingjing-Solo` 全目录复制进 ARC checkout**；只同步 `arc_adaptor` 声明的文件。
2. **不要覆盖 ARC 原生 `agents/__init__.py`、`agents/agent.py` 或其他官方 exports**。当前同步脚本虽然不复制 `agents/__init__.py`，但 ARC checkout 可能已有本地修改，必须先看 `git status` 和 `git diff`。
3. **不要把 ARC checkout 里的 `recordings/`、`.env`、`ARC_API_KEY` 或 Scorecard 输出提交回 Lingjing 仓库**。recording 是证据产物，按项目规则保存或引用，不作为源码 bundle。
4. **不要在 `LingjingSolo.choose_action()` 添加游戏分支**。新游戏应先走 profile/route artifact，再由 registry 注册专用 strategy。
5. **不要把 strategy 的抽象 action 和 ARC complex action 混为一谈**。复杂动作必须明确 `x/y` payload；缺少坐标时只能使用安全 fallback，并在 evidence 中记录。
6. **官方生命周期优先于 Lingjing 内部生命周期**：`NOT_PLAYED → RESET → observe/action → WIN/GAME_OVER` 必须由 ARC `FrameData` 驱动，不能用 Lingjing 内部状态替代官方状态。
7. **同步后必须在 ARC checkout 内运行 targeted tests**；在 Lingjing 根目录运行测试不能证明 ARC adapter、依赖解析和官方 runner 注册正确。

### 4.3 需要改变或补强的事项

当前统一闭环应把两个仓库的职责固定为：

| 位置 | 应承担的内容 | 不应承担的内容 |
|---|---|---|
| `Lingjing-Solo/` | 核心 Agent、R2/R3/R4/R5/CEAX、strategy source、schema、adapter tests | ARC 私有运行时副本、秘密、临时 Scorecard |
| `ARC-AGI-3-Agents/` | 官方 `FrameData`/`GameAction`/`GameState`、runner、在线环境和 Scorecard | 直接修改 Lingjing 核心、长期维护第二份 strategy source |

| `recording/verification` | requested action、server action、frame/state/level、hash、终态和 Scorecard 关联 | 仅凭 exit code、单个 bbox 或生成 UUID 宣称通过 |

下一步必须补强：

- 为 `sync_to_arc.sh` 增加 manifest/hash 检查，报告 source commit、ARC commit 和每个同步文件的 hash；
- 将 `agents/structs.py` 等 ARC 原生依赖缺失单独作为 checkout/dependency gate，不在 R11L 测试中静默修复；
- 将 R11L 的 `requested_action` 与 `server_action_input` 纳入统一 recording schema；
- 增加 ARC checkout 中的 `uv run pytest` targeted gate，并把完整 suite 的既有 Agent/Swarm API 漂移与 R11L 定向失败分开报告；
- 对 recording patch 做 `--check`、重复 apply 检测和 rollback 记录；
- 以后所有 Live/Scorecard 报告同时记录两个仓库的 commit，避免只记录 Lingjing commit 导致证据无法复现。

## 5. AR25、LS20、R11L 与未知游戏的统一适配方式

| 游戏/路径 | 观察 profile | R3/R4 方式 | 最小闭环证明 | 不能证明 |
|---|---|---|---|---|
| AR25 | 轴、拼块、目标、步骤、引擎状态 | 目标分解 → beam/state search → R4 回退 | 结构化配置能被真实/官方离线引擎 replay 并覆盖目标或 WIN | 只跑模拟器不证明真实引擎一致 |
| LS20 | 玩家、目标、墙、旋转/颜色/形状、动态平台、settled frame | A*/路线 artifact → 在线重规划 → R4 剪枝 | recording 重放重建 308 transitions，最终 `levels=7/state=WIN`；线上则需新 Scorecard | 旧 route 或生成 Scorecard 不自动证明当前代码仍通过 |
| CEAX unknown | 可见对象、动作 family、camera/visibility、状态/score | generic exploration + mode gate + bounded probe | 统一 recording 能解析、replay、并有真实终态/score | focus8 aggregate 或单个 L1 不证明所有游戏/所有机制 |

## 6. 统一三层跑测方法

### Tier A：Simulator / 纯逻辑测试

**目的**：验证模块逻辑、schema、边界和 deterministic planner。

可以证明：

- R2 能正确编码网格、哈希、差分；
- R3 在给定抽象状态上找到路径/配置；
- R4 评分、预算、fail-closed 和 tie-break 正确；
- R5 触发节流、prompt/context 构造、合法动作约束和技能迁移隔离正确；
- R11L probe/action-diff 能区分 `requested_action` 与 `server_action_input`，校验 64×64 frame、ACTION6 坐标边界、空合法动作和损坏 recording；
- CEAX mode gate 不允许错误动作 family；
- recording parser 对 RESET、nested action、frame stack 的处理正确。

不能证明：

- 游戏引擎的真实碰撞、镜像、动态平台、步数扣除；
- 线上 API、真实 camera、官方 Scorecard；
- 模拟器里没有建模的隐藏状态。

```bash

```

### Tier B：Offline Engine / 离线引擎闭环

**目的**：验证候选解能否在真实游戏逻辑/离线 ARC engine 中重放，并且能从 replay 生成 R2/R4 evidence。

必须包含：

1. reset；
2. 初始 observation；
3. planner/learner 生成 candidate；
4. action sequence 在离线 engine 中逐步执行；
5. 每步保存 settled frame、action、state、level；
6. replay parser 重建 Field transition；
7. 用权威 WIN/目标覆盖/level 终态判定。

```text

```

R11L replay 还必须保留请求动作和服务端回显动作两个字段：`requested_action` 用于验证策略选择，`server_action_input` 用于验证服务端实际接收的坐标；不得只用 diff bbox 推断 click 成功。

R4 当前已有真实 LS20 recording replay 证据；AR25 当前仍必须补齐真实原始 recording 和动作 payload 样本后，才能升级为真实 recording 证据。R11L 当前只有 reset/单动作 probe 和初始 profile，尚无可验证 Level 1 route，不能升级为全关离线或 Live 证据。

## 7. 团队统一验收门槛

### 7.1 模块级门槛

- R2：能从 recording 生成 stable observation 和 `(before, action, after)` transition；缺字段时明确失败。
- R3：候选 plan 引用输入 state hash，action 属于合法动作集合，搜索预算有界。
- R4：记录候选评分和选择理由；非法输入 fail-closed；dry-run 不产生 execute evidence。
- R5：记录触发信号、FieldSnapshot、假设/技能引用和建议是否被采纳；不允许绕过 R4 gate 或直接写入环境。
- CEAX：按 action family/visibility 门控；未知 game 使用 generic path；专用 route 通过 registry/profile 注入。

### 7.2 集成级门槛

至少通过：

1. schema validation；
2. empty input；
3. invalid input；
4. boundary limit；
5. existing recording 不被覆盖；
6. reset/idempotency；
7. partial failure fail-closed；
8. replay 后 transition/level/state 一致；
9. 安全权限和 secret 检查；
10. integration：真实或离线 engine 的端到端闭环。

以下项目在没有证据前必须标为 `not_verified`：

- restart adoption；
- rollback；
- 新游戏真实收益对比；
- AR25/ft09 原始 recording；
- R11L Level 1 route、六关 offline replay 和 6/6 Live Scorecard；
- 未知 CEAX 游戏的真实 Scorecard。

### 7.3 成功定义

一个游戏的“最小闭环通过”应满足：

```text
PASS =
  schema_valid
  AND actions_legal
  AND replay_complete
  AND terminal_or_goal_verified
  AND evidence_tier 明确
```

若要宣称“真实线上通过”，还必须：

```text
PASS_LIVE = PASS
  AND evidence_tier == live_scorecard
  AND new_scorecard/state/levels 有实际输出
```

## 8. 推荐的统一工作流

### Step 0：确定基线

- 所有人记录 branch、commit、game_id、profile 和运行模式；
- 先区分 simulator/offline/live，不允许混写；
- 通过 `arc_adaptor/MANIFEST.md` 和 strategy registry 确认 adapter 版本。

### Step 1：只做 observe/reset

- 采集初始 frame、legal actions、state、level、可见性和 action schema；
- 未知游戏先 observe-only；
- 发现 payload 或 frame stack 不确定时，先保存样本，不执行猜测动作。

### Step 2：接入 R2

- 生成 observation；
- 生成 stable state hash；
- 记录每个 action 的前后状态；
- 验证 RESET 会重新建 baseline。

### Step 3：接入 R3/R4/R5

- R3 只生成有界 candidate plan；
- R4 负责候选评分、反循环和预算；
- R5 在触发循环/冲突/预算信号时读取 FieldSnapshot，输出一个合法建议，并把 `reflection_id` 写回 decision；
- R5 建议必须再次经过 R4 合法性、预算和 action-family gate；
- decision 引用 observation/plan/reflection，不能只输出裸 action。

### Step 4：离线 replay

- 在 engine 或 recording replay 中执行；
- 生成 transitions 和 verification report；
- 失败时保留第一处 divergence：`tick/state_hash/action/expected/actual`。

### Step 5：有限真实执行

- 先 observe-only，再 single-action probe，再短 episode；
- 只在 action schema 和 fail-closed gate 通过后开放完整执行；
- 真实执行产物必须含 run manifest、recording、stdout 摘要和终态证据。

### Step 6：线上/Scorecard

- 只使用当前 branch 的干净 checkout；
- 记录新的 Scorecard ID、score、state、levels、actions、resets；
- 线上结果回写到 evidence report，不改写离线 evidence 的 tier。

## 10. 不允许的证据替换

以下说法禁止作为最终通过结论：

- “runner exit 0，所以游戏通关”；
- “生成了 Scorecard UUID，所以当前代码通过”；
- “模拟器找到了路径，所以真实引擎可执行”；
- “离线 cover report 通过，所以线上 AR25 已通过”；
- “视觉 delta 增加，所以动作有效”；
- “CEAX focus8 aggregate 提升，所以所有未知游戏能力已完成”；
- “recording 能解析，所以 recording 对应的代码版本和线上环境一致”。

正确写法必须同时说明：

```text
证据层级 + 代码基线 + game/profile + 终态字段 + artifact 引用 + 未验证项
```
