# Lingjing-Solo 统一跑测与验收方法

> **文档用途**：团队统一的跑测入口、证据分层和通过判据。
>
> **当前维护口径**：2026-10-11。本文只保留当前可执行的跑测流程；旧的 R2/R3/R4/R5/CEAX 设计、历史结果和已迁移路径不在本文重复维护。
>
> **适用范围**：
> - 项目根目录：`/srv/agent-platform/projects/Lingjing-Solo-/`
> - ARC Starter：`integrations/ARC-AGI-3-Kaggle-Starter/`
> - ARC runtime checkout：`integrations/ARC-AGI-3/`
>
> 代码测试、离线游戏通过和 Kaggle 官方隐藏集得分是三类不同结论，必须分开报告。

---

## 1. 四层跑测总览

```text
Tier A  核心 pytest / 契约测试
        验证 schema、理论、边界、fail-closed 和模块接口

Tier B  route replay / 单局离线 engine
        验证固定路线、action payload、状态迁移、终态和重复确定性

Tier C  benchmark_all_games.py 全量离线跑测
        验证 MyAgent 在全部本地游戏上的 aggregate 行为和逐局 scorecard

Tier D  Kaggle Notebook Phase A/B
        Phase A 验证 Kaggle Notebook 可执行
        Phase B 执行官方隐藏游戏集并取得官方分数
```

### 证据升级规则

- Tier A 通过：只证明代码/协议/逻辑满足测试，不证明真实游戏通关。
- Tier B 通过：证明指定 route 在真实离线 engine 中可重放，不证明全部本地游戏或 Kaggle 得分。
- Tier C 通过：证明当前 Agent 在当前本地游戏集合和步数上完成了一次全量离线运行，不证明 Kaggle 官方隐藏集结果。
- Tier D Phase A 通过：只证明 Notebook 在 Kaggle 环境完成运行。
- Tier D Phase B 通过：必须有新的官方提交结果、score、state 和 levels；不能用本地 JSON、kernel UUID 或 `exit 0` 替代。

所有跑测必须固定并记录：

```text
Lingjing commit
ARC runtime / framework commit
Starter commit
Agent 文件或 build tag
branch
运行模式
seed
游戏集合
max steps
输出 artifact 路径
```

## 3. Tier A：核心 pytest / 契约测试

### 3.1 目的

验证：

- schema 和公共接口；
- action 合法性、payload 边界和坐标边界；
- RESET、baseline、transition 和 recording parser；
- planner/search 的确定性、预算和 fail-closed；
- adapter 的依赖边界；
- 空输入、非法输入和已有 artifact 不被覆盖。

不能证明：真实 engine 碰撞、动态环境、线上 API、camera 行为或官方 Scorecard。

### 3.2 推荐入口

从项目根目录执行：

```bash
cd /srv/agent-platform/projects/Lingjing-Solo-
PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 python3 -m pytest -q \
  tests/test_ar25_field.py \
  tests/test_engine_action_adapter.py \
  tests/test_engine_solver.py \
  tests/test_recording_gate.py \
  tests/test_trajectory.py
```

如果变更涉及 AOP、DPL、v14 或其他模块，追加对应测试目录；不要把未运行的测试写成已通过。

### 3.3 Tier A 通过标准

- pytest 退出码为 0；
- 没有 collection error；
- 失败项按新增失败、已知 baseline 或环境缺依赖分类；
- 关键 invalid/empty/boundary/reset/idempotency case 有实际测试结果；
- 报告列出 `tests_run`、`tests_not_run` 和已知限制。

## 4. Tier B：route replay / 单局离线 engine

### 4.1 机器闸门

入口：

```text
integrations/ARC-AGI-3-Kaggle-Starter/tests/test_route_replay.py
```

路线文件：

```text
integrations/ARC-AGI-3-Kaggle-Starter/tests/routes/*.json
```

每条 route 至少包含：

```json
{
  "game_id": "bp35-0a0ad940",
  "target_levels": 1,
  "expected_state": "NOT_FINISHED",
  "actions": [{"a": "ACTION4"}],
  "meta": {
    "source": "...",
    "verification": "..."
  }
}
```

`ACTION6` 等带参数动作必须在 route 中保存 payload；测试通过 engine 的 `env.step(action, data=...)` 发送，不能只修改内存对象后宣称 payload 已验证。

### 4.2 执行命令

```bash
cd /srv/agent-platform/projects/Lingjing-Solo-/integrations/ARC-AGI-3-Kaggle-Starter
.venv/bin/python -m pytest -q tests/test_route_replay.py
```

该测试当前固定：

- `seed=0`；
- `OperationMode.OFFLINE`；
- 每条路线重放 3 次；
- 检查 `levels_completed` 和最终 state；
- 检查三次结果完全一致。

若 `arc_agi` 或 `arcengine` 未安装，测试会按现有 `importorskip` 边界跳过；此时必须报告为 `not_verified`，不能报告为 PASS。

### 4.3 Tier B 通过标准

每条路线必须满足：

```text
reset 成功
→ 初始 observation 可读取
→ action payload 到达 engine
→ 每步 state / level 可读取
→ 达到 target_levels
→ 终态符合 expected_state 或 WIN
→ 重放结果确定性一致
```

应保留：

- route JSON；
- engine/framework commit；
- route replay pytest 输出；
- 首个 divergence 的 tick、action、expected、actual；
- 如有 recording，则保存 recording 和 replay report。

单纯的几何配置解、模拟器路径、坐标变化或进程退出码都不能替代 route replay。

## 5. Tier C：全量本地 benchmark

### 5.1 标准命令

```bash
cd /srv/agent-platform/projects/Lingjing-Solo-/integrations/ARC-AGI-3-Kaggle-Starter

.venv/bin/python scripts/benchmark_all_games.py 400 \
  --agent agent/my_agent.py \
  --out ui/static/games_benchmark_<label>_offline_400.json \
  --label <label>
```

参数：

- `400`：每个游戏最多 400 action steps，不是运行 400 局；
- `--agent`：被测 Agent 文件；
- `--out`：完整逐局结果和 aggregate JSON；
- `--label`：应包含 branch/commit 或测试目的；
- 该脚本当前先创建 `OperationMode.NORMAL` 的 Arcade，异常时才回退到 `OperationMode.OFFLINE`；因此报告必须记录实际 engine 模式，不能仅靠输出文件名中的 `offline` 断言离线模式。

默认游戏集合来自 `environment_files/`。不同 `max_steps`、不同游戏集合、不同 Agent commit 或不同 environment commit 的结果不能直接比较。

### 5.2 结果检查

```bash
python3 - <<'PY'
import json
from pathlib import Path

p = Path("ui/static/games_benchmark_<label>_offline_400.json")
data = json.loads(p.read_text(encoding="utf-8"))
print({k: data.get(k) for k in (
    "total_games", "games_won", "total_levels_completed",
    "aggregate_score", "aggregate_score_official", "max_steps"
)})
for row in data.get("games", []):
    if str(row.get("state", "")).startswith(("ERROR", "SKIP")):
        print("NON_PASS", row)
PY
```

### 5.3 Tier C 通过标准

报告必须至少包含并人工检查：

- 总游戏数；
- `games_won`；
- `total_levels_completed`；
- aggregate score；
- 每局 `game_id`、`state`、`levels_completed`、`actions`、`game_score`；
- `ERROR`、`SKIP` 和异常字段；
- Agent、源码和环境 commit。

脚本会记录单局异常并继续跑其他游戏，因此**进程退出码为 0 不等于所有游戏通过**。

## 6. Tier D：Kaggle Notebook Phase A/B

### 6.1 Phase A：Notebook 可执行

准备：

```bash
cd /srv/agent-platform/projects/Lingjing-Solo-/integrations/ARC-AGI-3-Kaggle-Starter
make setup
```

`.kaggle/access_token` 只允许存在于本地，不能进入 Git、Notebook、日志或文档。`notebooks/kernel-metadata.json` 的 `id` 必须是当前实际使用的 Kaggle owner/slug；不要沿用其他账号的旧 owner。

本地先跑：

```bash
make verify-local                 # ls20 + vc33，50 steps smoke test
make play-local GAME=ls20        # 单游戏
make play-local                  # 本地全部游戏，默认 STEPS=200
```

构建、上传和查询：

```bash
make notebook
make submit
make status
```

Phase A 的通过证据：

- 当前账号/owner/slug；
- kernel URL 和 version；
- `make status` 显示 `complete`；
- Notebook 运行日志无未处理错误；
- 生成的 Notebook 与本地 Agent build 可对应。

Phase A **不等于**官方隐藏集得分。

### 6.2 Phase B：官方隐藏集提交

Phase A 完成后，在 Kaggle Notebook 页面执行 **Submit to Competition**，然后记录：

```text
competition
kernel ID / URL / version
submission ID（如有）
score
state
levels_completed
提交时间和账号
```

必须以官方新结果为准。不能用以下内容替代 Phase B：

- 本地 benchmark JSON；
- 本地 route replay；
- Notebook kernel UUID；
- `exit 0`；
- 只有启动成功、没有官方 score/state/levels 的运行。

官方提交额度有限：Tier A–C 未通过前，不消耗 Phase B 提交。

## 7. 统一 run manifest 与结果报告

每次 Tier B–D 跑测都应有一个 manifest 或等价记录，至少包含：

```json
{
  "schema_version": "lingjing-evidence-v1",
  "run_id": "...",
  "tier": "A|B|C|D-A|D-B",
  "game_id": "...|all",
  "agent_build": "git:<sha>|tag:<tag>",
  "project_branch": "...",
  "lingjing_commit": "...",
  "arc_runtime_commit": "...",
  "starter_commit": "...",
  "mode": "pytest|offline|live_scorecard",
  "seed": 0,
  "max_steps": 400,
  "status": "PASS|FAIL|BLOCKED|NOT_VERIFIED",
  "artifacts": [],
  "limitations": []
}
```

结果报告必须区分：

- `PASS`：当前层的全部判据有证据；
- `FAIL`：当前层实际运行但判据未满足；
- `BLOCKED`：依赖、账号、权限或环境阻止运行；
- `NOT_VERIFIED`：没有执行，不能据推断通过。

### 最小证据链

```text
代码/配置
  → 测试或 engine 执行
  → 原始 stdout / pytest result
  → JSON / recording / replay report
  → 终态字段和 score
  → manifest 中的 commit 与运行参数
```

## 8. 通用边界检查清单

每个新增 route、planner、action adapter 或 benchmark 改动，至少检查：

- [ ] happy path：正常路线/正常输入；
- [ ] empty input：空 frame、空 action 或空 route；
- [ ] invalid input：未知 action、损坏 JSON、缺字段；
- [ ] boundary limit：坐标、步数、候选数、payload 大小；
- [ ] existing state：已有 route/recording/output 不被错误覆盖；
- [ ] idempotency：重复 reset、重复 replay、重复 benchmark；
- [ ] partial failure：单局失败是否保留错误并继续或 fail-closed；
- [ ] restart adoption：重启后是否读取同一版本/状态；
- [ ] rollback：失败后是否有安全回退；
- [ ] security/permissions：token、权限、路径和 secret 不泄漏；
- [ ] integration：真实离线 engine 或 Kaggle 边界是否实际执行。

`restart adoption` 和 `rollback` 若未实际测试，必须标为 `not_verified`，不能因单元测试通过而勾选。

## 10. 不允许的结论替换

以下表述不能作为通过结论：

- “pytest 通过，所以真实游戏通关”；
- “route JSON 存在，所以 route 已验证”；
- “模拟器找到路径，所以真实 engine 可执行”；
- “benchmark 退出码为 0，所以全部游戏通过”；
- “Phase A kernel complete，所以取得官方隐藏集分数”；
- “生成 Scorecard UUID，所以当前 Agent 已通过”；
- “视觉 delta 增加，所以 action 成功”。

正确报告必须同时写明：

```text
层级 + 代码基线 + 运行参数 + 终态字段 + artifact + 未验证项
```
