## 2. ★ 官方评分口径：覆盖率就是分数乘数

官方 `Evaluation` 页与 `data-description` 页原文：

- *"Competition evaluation uses a separate, private set of **110 games** that your agent has never seen."*（55 局算 Public LB，55 局算 Private LB）
- 每关得分 `min(human/agent, 1)²`；每局按关卡序号加权平均；**总分 = 局分平均（0–100%）**。

**这条口径把整个优化方向钉死了**：

```
总分 = (1/110) × Σ(第 i 局得分)
     └─ 没跑到的局 = 0 分，直接拉低平均值
```

所以：

| 杠杆 | 作用方式 |
|---|---|
| **覆盖率**（9h/25h 窗口内能玩多少局） | **乘数**：110 局里只跑到 45 局 ⇒ 平均分直接砍掉 59% |
| **单局思考预算**（每局能给 LLM 多少秒） | **乘在单局分上**：5400s → 7920s 是每局 +47% 的推理时间 |
| **analyzer 旋钮**（thinking / tool_steps / yield / max_output） | 决定 agent **动不动手**——不动手则单局必然 0 |
| **vLLM admit limit** | 决定并发提升能否真正兑现（见 §4.3） |

### 3.1 ⚠️ 关于"覆盖率 45/110"这个数字，必须修正

我们之前（v27 方案文档）用的模型是：

> 9 h 窗口 ÷ (8 并发 × 5400 s) ⇒ 只能覆盖 45/110 局（41%），官方 28 × 7920 s = 4 波 ⇒ 110/110。

**这个模型的 9 h 窗口假设从未被验证**，而它恰恰是 v28 存在的全部理由。今天查到的证据指向**相反**的方向：

| 证据 | 值 | 推论 |
|---|---|---|
| duck v25 竞赛 rerun（ref 57459857） | 提交 10-21T01:16Z → COMPLETE 10-22T02:10Z = **约 25 小时** | 远超 9 h |
| v25 的 bench 配置 | concurrency 8 × 5400 s | 110 局全跑需要 13.75 波 × 5400 s = **20.6 h** 纯游戏时间 |
| v25 rerun 的 parquet | **3421 B** | 与 CPU 臂的 3509 B 只差 88 B |
| CPU 臂 rerun（ref 57542504） | 85.2 分钟、**3509 B** | CPU 臂快，必然跑满 110 局 |
| 1 行占位符 parquet | 2648 B | 基准 |

用"字节数 ∝ 行数"反推（该比值对基准不敏感，取 B₀ ∈ [2550, 2650] 结论一致）：

```
rows_v25 ≈ 110 × (3421 − B₀) / (3509 − B₀) ≈ 98 ~ 100 局
⇒ 98~100 局 ÷ 8 并发 × 5400 s ≈ 19.4 h 纯游戏时间 + 启动/排队 ≈ 25 h 墙钟
```

**⇒ 竞赛 rerun 的游戏时间预算约 20 h 量级，不是 9 h。**

**所以 v28 的真实收益要这样表述**（不是"45 → 84 局"）：

| | v27 | v28 |
|---|---|---|
| 并发 | 8 | **16** |
| 每局上限 | 5400 s | **7920 s**（官方值） |
| 死局提前放弃 | 无（开关在 overlay 里，卡在 v5） | **2700 s 生效** |
| 跑满 110 局所需时间（最坏情况） | 13.75 波 × 5400 = **20.6 h**（贴着预算边缘） | 6.875 波 × 7920 = **15.1 h**（有富余） |
| 跑满 110 局所需时间（典型，40% 死局提前放弃） | — | 6.875 波 × 5832 = **11.1 h** |

**⇒ v28 = 「从刚好铺满变成有 5~9 h 富余」+「每局思考预算 +47%」+「死局槽位提前释放」+「admit limit 匹配新并发」。**
这仍然是一次实质升级，而且**同时对两种可能都成立**：

- 若覆盖率确实曾经是瓶颈 → v28 直接受益；
- 若隐藏局比公开局难得多（v25 的 0.06 只有其 bench 预测的 1/9，可能就是这个原因）→ **每局 +47% 的思考预算**就是那个杠杆。

**唯一能彻底定案的实验**：把 CPU 臂（ref 57542504）的 rerun parquet 下一下来数行数。
Kaggle API 的 `competition_download_submission` 对我们账号是 **403**，只有网页能下 ⇒ 已列为 10-24 任务里的可选项。

### 4.2 ⚠️ 今天抓到的隐蔽坑：admit limit 写死 8 的地方有**三处**

`patch_v28.py` 最初写的锚点命中 0 次。逐字符取证后才发现：**cell 8 里把 `--max-num-seqs` 钉死成 8 的地方有三处**，写法各不相同：

| 处 | 位置 | 触发条件 | 是不是 v27 实际生效的那个 |
|---|---|---|---|
| **A** | `_vllm_extra` 注入分支 | 上游**没有** `--enforce-eager` | ✅ **就是它** |
| B | `for` 循环的替换值 | 上游自带 `--max-num-seqs` | ❌ |
| C | `else` fallback | 上游完全没提 max-num-seqs | ❌ |

**实测上游 `setup_commands.json`（10076 字符）：`--max-num-seqs` 出现 0 次，`--enforce-eager` 出现 0 次。**
⇒ 运行时 `if "'--enforce-eager'" not in _cmd` 恒为真 → **走 A 分支注入 `'--max-num-seqs', '8'`** →
之后 `for` 循环的候选 `('16','4','28','32')` 里没有 `'8'` ⇒ 不替换 →
`else` 分支因 `'--max-num-seqs',` 已存在 ⇒ 也不替换 ⇒ **最终 8**。

**⇒ 只改 B/C 而漏掉 A，v28 的并发提升会在 vLLM 的 admission gate 上排队，100% 落空。**

修法（`patch_v28.py::patch_max_num_seqs`）：不再手写精确字符串锚点（三种引号/缩进组合极易只命中一处，本次就踩了：
fallback 锚点多了一个前导 `"`，命中 0 次），改成**行级识别**——凡出现 `'--max-num-seqs'` 的行，
在它自己及随后 2 行内找写死的 `'8'`，命中数**必须恰好等于 3**，否则 `SystemExit` 响亮失败。

### 4.3 v28 的高保真验证（不是静态检查，是真跑）

## 5. 门控阈值：为什么不是 40.0

之前计划把门控下限抬到 **40.0（官方基线口径）**。**这个计划是错的，已改。**

| 版本 | 离线 25 局总分 | 有动作局 |
|---|---|---|
| v25 | 14.52 | 14/25 |
| **v27** | **18.61** | **19/25** |
| 官方基线 | 40.0 | — |

- 40.0 是**能力上限口径**。拿它当门控 ⇒ **v27 也被挡住**。
- 日提交配额只有 **1 次/UTC 日**，而我们历史最好分是 0.15。**拿一个已知能跑、bench 0.744/局（是我们历史最好分 5 倍）的版本去换 0 分，对冲榜是纯负收益。**
- 所以门控的职责是**挡"坏态"**（agent 一个动作都不出 / 服务器没起来 / 路径断了），**不是挡"不够强"**。

**最终阈值（已写进 `_gate_submit_duck.py`）**

| bench 模式 | 有动作局 | 总分 | 依据 |
|---|---|---|---|
| FULL（5400 / 7920 s 每局） | ≥ **15** | ≥ **12.0** | v27 实测 19 / 18.61，留 ~20% 余量；v25 的 14/25 会被挡 |
| SHORT（900 s 每局） | ≥ **8** | ≥ **4.0** | 900 s 与 5400 s 不可比，绝对分必然更低；主要挡"完全不动" |

**绝对分只用来挡硬坏态，真正的闸门是健康检查。**

### 7.2 P2 怎么落（这是真正的胜负手）

官方基线 1.6002/局 vs 我们 0.744/局，差 2.15 倍。**这部分差距不是并发、不是旋钮，是 agent 的"游戏理解"能力。**
按投入产出排序：

1. **通用化探索策略**（不知道动作语义的游戏要靠试）——直接命中"每关 `min(human/agent,1)²`"里 agent 步数比 human 大的那些局。
2. **跨局记忆 / 规则归纳**：同一个隐藏集里常有同族游戏，能复用的规则要复用。
3. **让 LLM 写代码做网格分析**：这正是官方 Duck harness 的强项（它给 LLM python 沙箱）。我们现在是"看图 + 选动作"，比"写代码分析网格"弱一个量级。

**注意：这三项都必须写在 agent 里，不能依赖公开 25 局的先验**——公开局计划对隐藏集贡献精确为 0（§1.1 已实证）。

### 7.3 还要不要继续合并？

**要，但目标变了。** 合并（符号级 + `check_call_signatures.py` 防线）的价值是**保住 Duck 线能持续吸收官方 harness 的升级**，而不是直接提分。
判定标准建议改成：**每次合并后必须能通过"离线 25 局 bench ≥ v27 基线 18.61"这条回归线**，否则不合并。
（合并前先用短 bench 跑一遍，8.3 h → 1 h，这条回归线才跑得动——这本身就是 v28 第 4 项改动的真正价值。）
