# 为什么一直是 0.15 分？—— 根因诊断与冲榜路线（2026-10-20）

> 结论先说：**0.15 不是因为 vLLM 慢、不是因为 agent 弱，是因为排行榜根本不用你们优化的那 25 个游戏。**
> Kaggle 公开榜在 **110 个隐藏局**上评分（55 局计公开榜 + 55 局计私有榜），
> 而你们 29 次提交的 SmartRouter 所有 INLINE plan（ls20/ar25/ft09/vc33/sb26/r11l/cd82/tn36/tr87/sc25/wa30/cn04/dc22/sp80/lp85/su15…）
> 全部按**公开 game_id** 路由 —— 在评测集里一次都不会触发。

## 2. 0.15 的构成：通用兜底路径的「随机蹭关」

- 公开榜 = 55 个隐藏局的 RHAE 均值。0.15 ≈ 通用路径（CEAX 探索 + Qwen 每步 JSON）偶尔完整通过 1–3 关、且效率极低（`(人类/agent)²` 后趋近于 0）。
- 参照系：**随机 agent 公开榜 0.10**。你们 0.15，只比随机高 0.05。
- 你们 9-03 提交的 ls20×2+ar25×1 硬编码也是 0.15 —— 硬编码没触发，0.15 全部来自兜底路径。
- 程序化（无 LLM）agent 的天花板已被第三方实测封死：**≈0.27**（BDR-Pro v54–v79）。

## 3. 为什么 LLM 路径也没救回来（v13/v15 仍 0.15）

v15 的 commit-mode 日志只证明「验证链」通到 `PHASE_B_FINGERPRINT` 就结束（dummy parquet 2648 字节 = `['1_0','1',True,1]`），真正的 rerun 日志在 Kaggle 侧看不到。但从配置可以推出四个死穴：

1. **并发饿死**：rerun 的 Swarm 对网关返回的**全部 110 个游戏同时起线程**，共享一个 `max_num_seqs=8` 的 vLLM。110 个循环每步都问 LLM（`LINGJING_LLM_EVERY=1`）→ 排队远超 45s 超时 → fail-closed 静默退回通用路径。
2. **又慢又浅**：32k 上下文 + 结构化视图 + 每步一问 + 800 次总上限 + 512 max_tokens。9 小时预算里模型时间是唯一瓶颈（第三方实测："essentially the entire budget is model time"，要到每局 L3 需持续 0.577 actions/s）。
3. **冷启动吃掉预算**：33.5GiB FP8 从 FUSE.GCSFUSE 随机读 1271s（v15 实测），约 9h 预算的 4%，且是 rerun 超时/失败的风险源（你们 duck kernel 的 `_last_out` 就死于 EngineCore 初始化）。
4. **架构代差**：每步返回一个 JSON 动作的「浅规划器」≠ 榜首架构。榜首 Tufa Labs（68.91）就是开源 Duck harness 的作者 —— **Qwen3.6-27B-FP8 + vLLM + Python REPL 写代码分析网格 + 分割工具 + 多模态 + 上下文驱逐**，公开集均值 1.60±0.45，其分支队拿到 2.37。

## 4. 进程失误：正确的 Kernel 被做过，但从未提交

- 10-12 你们自己的《高分队经验可用性分析》已给出正确结论：「Duck/本地 LLM+REPL 是榜分主路径」「按 game_id 再堆 plan 只涨本地」。
- 10-12 推送了平行 Duck kernel `liaojiaxuan/lingjing-duck-harness-v1` —— **Kaggle 状态 ERROR，且 29 次提交里 0 次是 duck**（vLLM `profile_run` 失败：GDN warmup 缺 `cutlass` 模块 + 显存 profiling OOM）。
- 同一时期你们连续提交了 7 次 SmartRouter（v9→v15，全部 ≤0.15）。**解法你们其实已经写过一遍**：SmartRouter kernel 靠 `--max-num-seqs 8 --enforce-eager --gpu-memory-utilization 0.90 --linear-backend cutlass VLLM_USE_FLASHINFER_SAMPLER=0` 修好了同一个坑（失败指纹表里有），只是没搬进 Duck kernel。

## 5. 关于「vLLM 读权重 21 分钟」的定位

你的 I/O 分析是对的（FUSE.GCSFUSE 随机读、auto-prefetch 未识别、每次 rerun 冷启动），但它**不是 0.15 的原因**——哪怕 1 秒加载完，plan 不触发照样 0.15。它的真实代价是 9h 预算和失败率。缓解按 ROI 排序：

1. 权重先 `cp` 到 `/kaggle/working`（容器本地盘）再启动 vLLM：顺序读比 FUSE 随机读快数倍，21min → 约 5–8min；
2. 复用 SmartRouter 已验证的启动参数（max-num-seqs=8 / enforce-eager / cutlass / mem 0.90），把 rerun 起不来概率压到 0；
3. `--safetensors-load-strategy=prefetch` 在「不识别的 FS」上日志已明说帮助有限，别指望；
4. 「保分提交先关 LLM」意义为零：关掉就是 0.15–0.27 的程序化天花板，榜上你们最好成绩本来就是 0.15，没有可保的分。

## 6. 冲榜路线（公开榜前十 = 41.74，榜首 68.91；今天 10-20，决赛提交截止 11-02，每天 1 次提交）

**诚实预期**：13 天从 0.15 到 41.74 是 270 倍，榜首队已迭代数月。前十概率极低；但下面每一步都有确定收益，且是唯一被公开验证过的路。

2. **提交后 1 小时内核验 publicScore 指纹**（R5 文档标准）：不上 1.0 就视为 rerun 没真跑，不要继续改 agent。

### P1 — 第二周（从 ~2 摸进 20–40 集群，集群内 1573 支队）

## 2026-10-22 补充（第二轮诊断）：本文结论**基本成立**，但两处要改口径

本文 §1 的核心判断——"评测集是 110 个隐藏局，本地分不迁移"——**被官方 `data-description` 页原文坐实**：

> Competition evaluation uses a **separate, private set of 110 games** that your agent has
> never seen. Half of these are used for the Public Leaderboard score, and the other half
> for the Private Leaderboard score.

**两处口径修正：**

1. **本文 §1 说"公开榜 = 55 个隐藏局的 RHAE 均值"，0.15 ≈ 通用路径偶尔蹭 1~3 关 —— 结论不变，且现在有官方评分公式背书**：
   每关分 `min(human/agent, 1)²`，每局分按关卡序号加权平均，总分 = 局分平均（0–100%）。
2. **本文说"0.15 全部来自兜底路径"是对的，但要补一条**：我们**另外还有一条独立的"通路断了"**——
   `build_notebook.py` 把竞赛 wheelhouse 路径写死成 `/kaggle/input/<slug>/…`，
   而正确路径是 `/kaggle/input/**competitions**/<slug>/…`（官方样例即如此）。
   路径不对 ⇒ `arc-agi` 装不上 ⇒ notebook 第 1 个 cell 抛错 ⇒ **agent 一局都没玩**。
   这解释了 0.00 那几次提交（**已修 + 已实测验证**：CPU kernel v1 ERROR → v2 COMPLETE）。
   **但它只能把 0.00 拉回 0.15，拉不到 20–40 集群**——后者只能靠 Duck harness 路线。

**详细证据链见** `docs/官方分支合并与SELFLEARN_LLM开关_分析报告_20261022.md` 第 8 章。

## 2026-10-22 补充（第三轮诊断）：并发退化的真正根因 —— `GameAction` 枚举单例被并发写坏

本文说 0.15 是「通路断了 + 隐藏集没计划」两件事。**第三轮又挖出第三件事，而且它是可修的 bug，不是能力问题**：

> **25 局并发把 13 局 WIN 砍成 3 局 WIN（1510 → 408.20 分）。**

**根因不是「跑得慢」，是共享可变状态被并发写坏：**
`arcengine.GameAction` 是**枚举单例**，`ACTION6` 全进程只有一个实例；
`action.set_data({x,y})` 直接把坐标写在这个共享成员上，而框架要等下一行才
`action.action_data.model_dump()` 读回来发出去。竞赛 rerun 里 25~110 局 = 25~110 个线程共用一个进程，
于是 **A 局刚写好的点击坐标被 B 局的 `set_data` 覆盖 → A 局的点击落到 B 局的格子上 → 计划型动作全线跑歪**。

**证据链（三条互相独立）：**

| 证据 | 内容 |
|---|---|
| 单局对照 | 同一网关下 `--game cd82` → **100.00 分 / 6 关 / 73 步**（与顺序基准一致）；25 局并发 → **2 关 / 800 步** |
| 逐帧比对 | 前 6 步（非点击动作）与单局**逐像素一致**，**从第一个 ACTION6 起分叉**；被点的精灵在单局里移动了，在并发里原地没动 |
| 单元级复现 | 8 线程各写不同坐标再读回：原始 arcengine **10.8%~13.9% 坐标被串**，打上线程隔离补丁后 **0 / 24000** |

**已落地修复：** `my_agent.py` 把 `GameAction.action_data` / `reasoning` 改成**线程本地**存储
（property + `threading.local()`；框架代码一行不用改——竞赛 rerun 的框架树来自 Kaggle 官方 input 包，改不了）。
修复后 25 局并发复刻里 **cd82 回到 6 关 / 73 步**，与单局、顺序基准完全一致。

**⇒ 对提交的直接影响：10-23 要交的 CPU 保底版必须带这个修复，否则交上去的还是被写坏的版本。**
**详见** `docs/官方分支合并与SELFLEARN_LLM开关_分析报告_20261022.md` §8.11。
