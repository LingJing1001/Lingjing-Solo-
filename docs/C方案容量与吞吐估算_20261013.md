## 1. 模型（四条公式，全部可在代码里复核）

1. **权重显存** `W = params × bits/8 × overhead`（overhead=1.06，覆盖量化 scale 与未量化部分）
2. **每 token KV** `2 × layers × kv_heads × head_dim × kv_bits/8`；MLA 结构改用 `layers × mla_kv_dim`
3. **单轮延迟**（一轮 = 一次并发 batch 的完整 prefill + decode）
   - prefill 是**算力受限**：`2N × 未命中前缀 token / (峰值 × MFU)`，MFU=0.35
   - decode 是**带宽受限**：每生成一个 token 读一遍权重 + **全部常驻 KV**，
     `t = (W + 常驻KV) / (带宽 × MBU)`，MBU=0.75
4. **总耗时** `= ceil(总调用数 / 并发) × 单轮延迟`

**两条关键语义（都不是默认就能写对的）**：

- **并发 = 在飞的 LLM 调用数，不是局数**。上限由显存决定；并发 > 局数意味着单局同时有多个调用在飞
  （多 pass / 多分支），这正是 Duck "20 passes" 的形态。第一版写成"并发 ≤ 局数"是错的，已修。
- **共享前缀只存一份**。并发序列共用的那段（system prompt + 对象图模板）由 PagedAttention 块共享 /
  RadixAttention 基数树存一份，因此它同时抬高并发上限、压低单轮 KV 读取量。

硬件与模型规格都在 `HARDWARE` / `MODELS` 里，**`fp8_tflops` 是假定值**，换真机后应替换为 profile 结果。
（decode 是带宽受限，prefill 只占 1%，所以该假定对结论不敏感。）

## 2. 基线结果

场景：**27B-FP8 / RTX PRO 6000 96GB / 16 局 × 400 步 / ctx 12k / out 400 / 命中 0.85 / 共享前缀 0（保守）**

```
[显存]
  权重占用          : 26.65 GiB
  每 token KV       : 128.00 KiB
  KV 可用预算       : 57.59 GiB  → token 槽位 471,741
  并发              : 39  (显存上限 39)
    ⚠ 并发 > 局数(16)，等价于单局 2.4 个调用在飞（多 pass / 多分支）

[延迟]
  prefill           : 277.7 ms   (占比 1.0%)
  decode            : 26,774.3 ms
  单轮合计          : 27.05 s

[总账]
  调用数 6,400  →  165 轮
  总耗时            : 74.4 min  (预算 540 min)
  预算内可完成步数  : 46,710
判定 : OK    绑定约束 : none
```

**时间不是瓶颈**：基线 74.4 min，预算 540 min，**余量 7.3×**。

## 3. 五个杠杆，两个被误解

| 维度 | 量级变化 | 是不是杠杆 |
|---|---|---|
| **输出 token 数** | 64→1600 tok：13 → 295 min | ✅ **线性第一杠杆** |
| **上下文长度** | 2k→24k：13 → 151 min | ✅ **线性**（但机制不是你想的那个，见下） |
| **并发数** | 1→39 路：988 → 74 min | ✅ **线性**，且**必须开到显存上限，不要按局数卡** |
| **共享前缀长度** | 0→9000 tok：74 → 19 min | ✅ **3.9× 提速，杠杆之王** |
| 前缀缓存**命中率** | 0.0→0.99：79 → 74 min | ❌ **只有 6%，几乎不值钱** |

### 3.1 被误解一：要优化的是 decode，不是 prefill

`prefix_hit` 从 0.0 拉到 0.99，总耗时只降 6%。原因干净利落：

```
prefill 占单轮的 1.0%，decode（带宽受限）占 99.0%
```

⇒ **「prefix cache 省 prefill」这条在 LLM+REPL 场景下几乎不值钱。**
我们上一轮从 Duck 拆解里读到的"跨轮 prefix cache 是核心杠杆"——**位置对了，理由错了**。

### 3.2 被误解二（也是本次最大收获）：前缀缓存的价值在**显存**，不在算力

把 `shared_prefix` 单独拉出来看：

```
scenario                 W(GiB)  KV/tok conc   T/iter    T(min)     cap(dec)  verdict binding
shared=0                   26.7     128   39     27.1        74       46,710  OK     none
shared=1000                26.7     128   42     26.9        68       50,668  OK     none
shared=2000                26.7     128   46     26.8        63       55,575  OK     none
shared=4000                26.7     128   58     27.1        50       69,466  OK     none
shared=6000                26.7     128   77     27.1        38       92,222  OK     none
shared=9000                26.7     128  154     27.2        19      183,650  OK     none
```

**总耗时 74 → 19 min（3.9×），但单轮成本几乎不变（27.1s → 27.2s），并发 39 → 154 路。**

机制是：公共前缀只存一份 → 腾出显存 → 抬高并发 → 轮数变少。
这就是教程 Task3（PagedAttention 块共享 / RadixAttention 基数树）对 C-Local 的**真实价值**。
**取到的精华在这一点上，而它跟我们原先的理解方向不同。**

### 3.3 上下文长度：线性，但机制是"轮数"不是"单轮"

ctx 2k→24k 总耗时 13→151 min（**12.0×**），而**常驻 KV token 几乎不变**（470,000 vs 456,000）。

```
ctx=2000                   26.7     128  235     26.9        13      283,063
ctx=12000                  26.7     128   39     27.1        74       46,710
ctx=24000                  26.7     128   19     26.9       151       22,917
```

机制：常驻 KV 被显存钉住 → 单轮成本恒定 → **总耗时 ∝ 轮数 = 调用数 / 并发，而并发 ∝ 1/ctx**。
所以"上下文越长越慢"是对的，但**慢在并发放不下，不是慢在算得久**。

### 3.4 模型选型：直到 70B 都还在预算内

```
qwen3-4b-fp8                3.9      72   97     26.8        30      117,074  OK     none
qwen3-27b-fp8              26.7     128   39     27.1        74       46,710  OK     none
qwen3-27b-int4kv4          13.3      64   96     27.0        30      115,174  OK     none
llama-70b-fp8              69.1     160    8     27.5       366        9,431  OK     time
mla-30b-fp8                29.6      34  139     27.2        21      165,480  OK     none
```

70B-FP8 权重 69.1 GiB，只剩 15.1 GiB 给 KV → 并发被压到 8 路 → 366 min（余量只剩 1.5×），**binding=time**。
⇒ **27B 是"能力/余量平衡"的选点，不是被迫的妥协。**

## 4. 与 Duck 实测的交叉佐证

| | Duck 报告 | 本模型 |
|---|---|---|
| 卡 | 单卡 96GB | RTX PRO 6000 96GB |
| KV 池 | 1M+ token | 471,741 token 槽位 |
| 并发 | 10~16 局 | 39 路（=在飞调用数） |
| 耗时 | 75 min 每局 | 16 局 × 400 步 = 74 min |

**并发与耗时同量级**（16 路 / 75 min vs 39 路 / 74 min）→ 模型数量级可信。
1M token 池需要 4 个 KV head（或更小模型）才能达到，属合理差异；把共享前缀算进去后并发还可再提升。

## 5. 结论与对 C 的判断

1. **时间不是瓶颈**：27B-FP8 基线 74.4 min / 540 min，余量 **7.3×**。
   换算成"每步允许多少次 LLM 调用"：`calls_per_decision=5` → 370 min 仍 OK；
   `=8` → 592 min 已 TIGHT。**即每步最多约 7.3 次调用**。
2. **显存才是瓶颈**：并发上限 39 路由 KV 预算 57.6 GiB 决定。
3. **三个线性杠杆**：输出 token 数、上下文长度、并发数。
4. **一个杠杆被我们误解过**：前缀缓存的价值在**共享省显存 → 抬并发**（3.9×），
   不在省 prefill（6%）。

**对 C 的决策影响**：上一轮说"C 的成本主要是工程、算力官方白给"——算术证实了这一点，
并且进一步说明 **9h 预算对 27B 级模型是宽裕的**。真正要投入的是：
权重分发、serving 栈离线安装、请求网关（因为 `enable_internet=false` 必须在 notebook 内自洽），
以及**让并发真实开到显存上限**的调度（多 pass / 多分支 harness），而不是抠上下文长度。

---

## 6. 已知的模型局限（下一步要补的）

1. **没有实测校准**：`fp8_tflops` / `MFU` / `MBU` 都是假定值。拿到 RTX 6000 后第一件事是用
   `vllm bench serve` 把这三个数换成真值，重跑本模型。
2. **prefill / decode 简单相加**，未建模 continuous batching 的重叠（chunked prefill 会让两者并行）。
   这是**保守**方向，真实吞吐应当更好。
3. **未建模投机解码 / MTP**：教程 Task2 提到投机解码能让每轮推进多个 token，
   这是继"共享前缀"之后**下一个量级的杠杆**，本模型完全没有覆盖。
4. **未建模多轮上下文驱逐**：把 `ctx_tokens` 当作稳态值处理，未建模"历史增长 → 驱逐 → 回落"的动态。
